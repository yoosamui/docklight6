Docklight 6 has a solid layered core: platform-specific window handling is isolated behind a backend interface, while the UI consumes a
  normalized application/window model. The main architectural weakness is concentration of behavior in several very large GTK controller/widget
  files, plus a few build and documentation inconsistencies.

  ## Architecture

  main.cpp
   ├─ DockConfigurationManager ── config file monitoring
   ├─ DockMonitorManager ──────── monitor selection/topology
   ├─ WindowSystemController
   │    ├─ WindowBackend
   │    │    ├─ KWin Wayland backend ← D-Bus ← KWin script
   │    │    └─ EWMH/X11 backend
   │    │         ├─ KWin
   │    │         ├─ Marco/Metacity
   │    │         ├─ Muffin
   │    │         ├─ Mutter
   │    │         ├─ Openbox
   │    │         └─ Xfwm4/fallback
   │    └─ WindowRegistry ─────── normalized windows/app groups
   └─ DockWindow
        ├─ DockWindowController ─ layout, previews, autohide coordination
        ├─ DockItem ───────────── launcher UI and user interaction
        │    └─ DockApplicationController ─ application/window action policy
        ├─ LauncherManager
        ├─ DockPreviewWindow
        └─ DockAutohideController

  Startup is composed explicitly in src/main.cpp:88: configuration and window integration start first, then monitor selection and the main dock
  window are created. Configuration and monitor changes are propagated using sigc++ signals.

  ### Core domain and platform boundary

  The cleanest part of the design is src/windowing/window_backend.h:53. It defines:

  - Normalized window snapshots.
  - Capability flags.
  - Window actions such as activate, minimize, maximize, close, and icon geometry.
  - Signals for incremental state changes and reconnection.

  src/windowing/window_registry.h:44 sits above it and:

  - Mirrors backend state.
  - Normalizes .desktop identities.
  - Groups windows into running applications.
  - Maintains active-window and stacking order.
  - Guards operations using backend capabilities.

  This prevents KWin, D-Bus, XIDs, and libwnck objects from leaking into application-level code.

  ### Backend selection

  src/integrations/window_system_controller.cpp:235 selects the backend at runtime:

  - KDE Wayland → KWinWindowBackend.
  - X11 → KWin, Marco/Metacity, Muffin, Mutter, Openbox, xfwm4, or generic EWMH backend.
  - Other Wayland compositors → dock runs without window integration.

  Openbox previews require an X11 compositor. If no compositor owns the
  standard _NET_WM_CM_Sn selection, DockLight keeps the dock running, disables
  display_preview in the configuration, and presents a warning.

  The X11 implementations share src/integrations/x11/ewmh_window_backend.h:14, with WM-specific overrides where required.

  KWin Wayland is more distributed:

  1. The KWin JavaScript extension observes workspace.
  2. It publishes versioned window snapshots over session D-Bus.
  3. KWinIntegrationService validates and decodes the messages.
  4. KWinWindowBackend commits snapshots to the registry.
  5. Window commands travel back through WaitForCommand.

  The protocol is currently version 7 in both src/integrations/kwin/kwin_integration_protocol.h:33 and the kwin/org.docklight6.windowintegration/
  contents/code/main.js:10.

  ### UI and policy layers

  src/dock/dock_window.h:50 owns the GTK surface, items, tooltip, launcher manager, and controller.

  The design makes several useful policy/UI separations:

  - src/application/dock_application_controller.h:62 handles grouped application actions and workspace policy.
  - src/layout/dock_layout_engine.h:34 is a pure geometry calculator.
  - src/autohide/dock_intellihide_policy.h:33 is a pure overlap calculation.
  - DockWindowController coordinates layout, previews, icon geometry, media playback, and autohide.

  Live configuration is stored in ~/.config/docklight6/docklight.conf; attached launchers are stored separately as docklight.data.

  ## Main findings

  1. Installed CSS path is coupled to the source tree.
     main.cpp loads SOURCE_DIR/style.css at runtime src/main.cpp:152. SOURCE_DIR is compiled as the absolute source path src/Makefile.am:23,
     while style.css is not installed by the top-level data rules. A packaged binary may lose its main stylesheet when the build source is
     removed.

  2. Release tests disable most C++ checks.
     Release mode defines NDEBUG in build.sh, but the C++ tests use approximately 500 assert() calls. Consequently, make check against the
     release build reports success with most assertions compiled out. build.sh warns about this combination and the setup documentation directs
     full validation through debug mode. Tests should eventually use an always-active assertion framework or remove NDEBUG from test targets.

  3. README and implementation disagree about KWin/X11.
     The README says KWin X11 selects EwmhFallbackWindowBackend README.md:22, but the selector returns KWinX11WindowBackend.

  4. Runtime modularity does not extend to the build.
     PipeWire, Wayland, KDE screencast generation, and X11 libraries are all mandatory. An X11-only or unsupported-Wayland build still needs
     every development dependency.

  5. Several classes are maintenance hotspots.
     DockPreviewWindow.cpp is about 2,815 lines, DockItem.cpp 2,188, DockWindow.cpp 1,803, and DockWindowController.cpp 1,678. The domain/backend
     seams are good, but the GTK presentation layer would benefit from smaller interaction, animation, menu, preview-cache, and geometry-
     publishing components.

  ## Verification

  A clean non-NDEBUG build passed 12 test targets. The KWin D-Bus integration test could not create its temporary D-Bus socket inside the
  sandbox, so that specific test remains unverified here. The repository remained clean; no source files were changed.

• Docklight 6 has a well-separated, signal-driven architecture:

  - GTKmm handles the dock UI.
  - WindowRegistry provides a platform-neutral window/application model.
  - WindowBackend isolates KWin/Wayland and EWMH/X11 integrations.
  - Pure layout and intellihide policies are independently testable.
  - KWin integration uses a versioned D-Bus protocol, PipeWire, and KDE screencast APIs.

  Main concerns:

  - Installed CSS incorrectly depends on the original source-tree path.
  - Release builds define NDEBUG, disabling most C++ test assertions.
  - README incorrectly documents the KWin/X11 backend.
  - All Wayland, PipeWire, and X11 dependencies are mandatory at build time.
  - Several UI files exceed 1,500–2,800 lines and should be split.

  Overall: the core abstraction is strong, but packaging, test reliability, documentation drift, and oversized UI components need attention.
